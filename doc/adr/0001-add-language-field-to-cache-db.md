# 0001. Cache Database Language Field Addition

- **Status**: Accepted
- **Date**: 2026-07-20
- **Deciders**: USER, Antigravity

## Context (背景と課題)

AST-Digger が解析対象とするターゲット言語に TypeScript と Go を追加するにあたり、キャッシュ用 SQLite データベース (`symbols.db`) に保存されるメタデータ設計を見直す必要が生じました。

現状の設計では、ファイルパス (`files.path`) のみから拡張子を都度解析して言語を判別することが可能ですが、以下の課題が発生します：
1. クライアントや CLI が特定の言語のみのシンボルを高速にクエリしたい場合に、`LIKE` 句などを用いた不正確または非効率な文字列マッチングを行う必要がある。
2. 以降のフェーズ（スケルトン生成や参照探索など）で各モジュールがファイルの言語を必要とするたびに、ファイルパスのパース（拡張子の抽出とマッピング）を重複して実行しなければならず、ロジックが分散する。
3. 将来的に拡張子のないスクリプト（シバン `#!/usr/bin/env python` から判定）や、Markdown などのドキュメントに埋め込まれた多言語コードを解析したくなった場合に、拡張子のみに基づいた静的なマッピングでは言語を解決できなくなる。

## Decision (決定事項)

キャッシュデータベースのファイル追跡テーブル `files` に、ファイルに対応するターゲット言語を識別するための `language` フィールドを明示的に追加します。

### スキーマ定義の変更
```sql
CREATE TABLE files (
    path TEXT PRIMARY KEY,       -- プロジェクトルートからの相対パス
    mtime REAL NOT NULL,         -- 最終更新日時
    hash TEXT NOT NULL,          -- ハッシュ値（SHA-256）
    language TEXT NOT NULL       -- 解析言語 ("python", "typescript", "go" など)
);
```

ファイルスキャンおよび同期プロセスにおいて、拡張子 (および将来のシバン等) から言語を一度だけ判別し、このフィールドに記録します。パースやクエリを実行する全てのモジュールは、この `language` フィールドを利用して言語特有の処理に振り分けます。

## Consequences (結果と影響)

- **Positive (メリット)**
    - 特定のターゲット言語に絞り込んだシンボルのクエリ (例: `WHERE language = 'typescript'`) が極めて高速かつ正確になる。
    - 言語判別ロジックがキャッシュ同期プロセス（初回スキャン時）に一元化され、他の機能での冗長な拡張子判別コードが不要になる。
    - シバンから言語を判定するファイルや埋め込み多言語など、将来の拡張への耐性が確保される。
- **Negative (デメリット/コスト)**
    - キャッシュデータベースの容量が微増する（ごく少量の文字列データのため、実質無視可能）。
    - スキーマ変更に伴い、既存のキャッシュデータベースが接続された際、マイグレーション処理または破損検知による自動再構築が必要になる。
- **Risks (リスク)**
    - 新しいターゲット言語が追加された際に、`language` フィールドに格納する文字列の Enum 値の定義および判別処理を適切に更新する必要がある。

## Considered Alternatives (検討した選択肢)

- **ファイル拡張子によるオンザフライ判定**
    - Pros: データベーススキーマが極めてシンプルに保たれ、カラム追加が不要。
    - Cons: 重複する判定ロジックが各所に散らばり、DBクエリ時の言語別フィルタリングが非効率。拡張子のないファイルや埋め込み言語に対応できないため却下。
