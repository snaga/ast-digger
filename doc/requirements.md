# 要件定義書 (requirements.md)

## 概要

AST-Diggerは、AIエージェントが大規模なコードベースを効率的に探索するための構文解析・コード抽出ツールである。AIエージェントが大規模なファイルを丸ごと読み込むと、コンテキスト窓の浪費やノイズによる推論精度の低下が発生する。本ツールは、tree-sitterを活用してAST（抽象構文木）を解析し、クラスや関数のスケルトン（アウトライン）、指定されたシンボル名に基づくピンポイントの実装コード、呼び出し関係（Callers/Callees）、およびディレクトリ全体の構造化アウトライン（SQLiteによる差分更新キャッシュ付き）を高速に提供する。また、ランタイムに依存しない単一バイナリとして配布・実行できることを目指す。

## 前提条件

- 開発・ビルド環境に Go 1.22 以上のツールチェインがインストールされていること。
- 実行環境には Go ランタイムのインストールは不要（コンパイル済みの単一バイナリとして配布・実行されるため）。
- 解析対象のプロジェクトディレクトリに Python, TypeScript, Go, Java, JavaScript, Rust のソースコード、Markdown ドキュメント、または SQL（Snowflake/ANSI）スクリプトが存在すること。

## 制約条件

- 解析のターゲット言語・ドキュメント（解析対象ファイル）として、Python, TypeScript, Go, Java, JavaScript, Rust, Markdown (`.md`, `.markdown`), および SQL (`.sql`) をサポートする。
- ローカル環境でネットワーク接続を行わずに完全自己完結で動作しなければならない。
- 構文解析エンジンとして tree-sitter（Go バインディング）を使用し、仮想環境のライブラリ依存などの完全な解決（LSPレベルの動的な型解決等）は行わない。

- **CGO依存を許容する**: tree-sitter の Go バインディングは CGO に依存するため、`CGO_ENABLED=0` での完全ピュアGoビルドは要求しない。ビルドホストにはCコンパイラ（gcc/clang等）が必要であることを前提とする（[`tech.md`](./tech.md) の「CGO 依存に関する既知の制約」を参照）。
- **クロスコンパイルはスコープ外とする**: CGO依存を受け入れる代償として、`GOOS`/`GOARCH` を切り替えたクロスプラットフォームビルド（例: Linux上でWindows/macOS向けバイナリを生成する）はスコープに含めない。各ターゲットプラットフォーム向けのバイナリは、そのプラットフォーム上でのネイティブビルド（`go build`）によって生成する運用とする。詳細は [ADR-0005](../doc/adr/0005-accept-cgo-and-descope-cross-compilation.md) を参照。
- **CLIの呼び出し規約**: サブコマンド名、引数名、オプション名（`--json` / `-j` を含む）、テキスト/JSON出力のフォーマットは一貫した規約に沿って定義され、エージェントが容易に呼び出せるようにしなければならない。

## 要件

### 要件カテゴリA: コードのアウトライン抽出 (Skeleton / Outline Extraction)

- 要件 A-1: ファイルアウトラインの取得
   - ユーザーストーリー
      - 私はAI開発エージェントとして、特定のソースコードファイルの全体構造を把握したい。なぜなら、中身の実装コード（ノイズ）を読まずに、どのようなクラスや関数が定義されているかをトークン消費を抑えて知るためだ。
   - 受け入れ基準
       - エージェントが対象ファイルのパス（`.py`, `.ts`/`.tsx`, `.go`, `.java`, `.js`/`.jsx`, `.rs`）を指定して`outline`コマンドでアウトライン取得を要求したとき、システムはファイルをtree-sitterで解析し、各言語に対応した定義（Python: クラス/関数/デコレータ/docstring、TypeScript: クラス/インターフェース/タイプ/関数/JSDoc、Go: 構造体/インターフェース/関数/doc comments、Java: クラス/インターフェース/enum/メソッド/コンストラクタ/Javadoc、JavaScript: クラス/関数/アロー関数/JSDoc、Rust: struct/enum/function/impl/trait/mod/doc comment (`///`, `//!`)）のシグネチャのみを含み、実装コード部分が省略された（`...`または`{ /* ... */ }`に置換された）スケルトンコードを生成して出力しなければならない。
      - 対象ファイルに構文エラーが存在するとき、システムはパースに成功した部分のスケルトンコードを組み立てて出力し、標準エラー出力に警告メッセージを出力しなければならない。

### 要件カテゴリB: ピンポイントコード抽出 (Targeted Symbol Extraction)

- 要件 B-1: シンボル指定によるコード抽出
   - ユーザーストーリー
      - 私はAI開発エージェントとして、特定のクラスやメソッドの実装コードだけをピンポイントで取得したい。なぜなら、修正すべきロジックの範囲だけにLLMの注意を向けさせ、トークン消費を最小限にするためだ。
   - 受け入れ基準
      - エージェントが対象ファイルのパスとシンボル名（例: `UserManager.register_user`、`UserService.getUser`、`Handler.ServeHTTP`、`UserRepository.findById`（Java）など）を指定して`symbol`コマンドでコード抽出を要求したとき、システムは対象のASTノードからその範囲の実装コード全体（行範囲）を正確に切り出し、テキストとして出力しなければならない。
      - 対象のシンボル名がファイル内に存在しないとき、システムはエラーメッセージを出力し、終了コード4で処理を終了しなければならない（要件H-3参照）。

### 要件カテゴリC: 呼び出し関係探索 (Call Graph & Reference Tracer)

- 要件 C-1: 呼び出し元（参照箇所）の探索
   - ユーザーストーリー
      - 私はAI開発エージェントとして、特定の関数やメソッドがどこから呼び出されているか（参照されているか）を知りたい。なぜなら、その関数を修正した際の影響範囲を正確に特定するためだ。
   - 受け入れ基準
      - エージェントが`references`コマンドでプロジェクト全体から特定のシンボル名（例: `register_user`）の参照探索を要求したとき、システムは`--project-root`配下の全対応ファイルをスキャンし、tree-sitterでパースして、該当シンボルが呼び出されているファイル名と行番号（および呼び出し行のコードスニペット）の一覧を出力しなければならない。コメントアウトされた部分や文字列リテラル内の出現は除外しなければならない。

### 要件カテゴリD: 定義および依存インポート解決 (Smart Import Resolver)

- 要件 D-1: インポート先の追跡
   - ユーザーストーリー
      - 私はAI開発エージェントとして、あるファイル内でインポートされている外部/ローカルモジュールの実際の定義場所を突き止めたい。なぜなら、インポート先のシンボルの実装を確認するためにファイル間をスムーズに移動したいためだ。
   - 受け入れ基準
      - エージェントがファイルパスとインポートされているシンボル名を指定して`resolve-import`コマンドで定義探索を要求したとき、システムは対象ファイルのインポート文（Pythonの`import`/`from...import`、TypeScriptの`import...from`、Goの`import`、Javaの`import`（単一/ワイルドカードインポート）、JavaScriptの`import...from`（ES Modules））をAST解析し、該当モジュールのファイルパスと、定義されている開始行を解決して出力しなければならない。

### 要件カテゴリE: ディレクトリ構造化アウトライン (Directory/Module Outline with SQLite)

- 要件 E-1: キャッシュデータベースの自動構築と差分更新
   - ユーザーストーリー
      - 私はAI開発エージェントとして、プロジェクト全体のファイル構成とそこに定義されている公開シンボルの一覧を高速に把握したい。なぜなら、巨大なプロジェクトでも待ち時間なしで全体像をロードするためだ。
   - 受け入れ基準
      - エージェントが`directory`コマンドでディレクトリのアウトライン取得を要求したとき、システムはサポート対象言語の拡張子（Python: `.py`、TypeScript: `.ts`/`.tsx`、Go: `.go`、Java: `.java`、JavaScript: `.js`/`.jsx`）を持つファイルをスキャン対象とし、初回時に`.workspace_cache/symbols.db`（SQLite）を作成し、全ファイルをパースしてシンボル情報を保存しなければならない。
      - 2回目以降の要求時に、ファイルが更新されているとき（mtimeが異なる、またはファイルが新規・削除された場合）、システムは該当するファイルのみを部分的に再パースし、SQLite内のインデックスを増分更新（差分スキャン）した上で、最新のツリー情報（ファイル階層＋各ファイル内の定義シンボル一覧）を出力しなければならない。
      - ファイルに変更がないとき、システムは再パースを行わずにSQLiteからデータを即座にロードして出力しなければならない。
      - キャッシュデータベース（`.workspace_cache/symbols.db`）のテーブル定義（テーブル名・カラム名・型・インデックス）は [`design.md`](./design.md) の「キャッシュデータモデル」節の定義に従わなければならない。

### 要件カテゴリF: 自己内省とフリクションフィードバック (Introspection & Feedback)

- 要件 F-1: 機械判読可能なコマンドメタデータの出力
   - ユーザーストーリー
      - 私はAI開発エージェントとして、ツールの持つ機能や引数の型情報を自動で認識したい。なぜなら、仕様書を再読することなく、動的にコマンド呼び出しを組み立てて実行するためだ。
   - 受け入れ基準
      - エージェントが自己内省（`agent-context`）を要求したとき、システムはツールの全サブコマンド、引数、オプションを定義したJSONスキーマを出力しなければならない。

- 要件 F-2: 動作フリクションのローカル記録
   - ユーザーストーリー
      - 私はAI開発エージェントとして、ツールのバグや解析失敗などの問題を自動で報告したい。なぜなら、問題の存在を素早く記録し、後から改善につなげてもらうためだ。
   - 受け入れ基準
      - エージェントがフリクション報告（`feedback`）を要求したとき、システムは渡されたメッセージとタイムスタンプを、`.workspace_cache/feedback.jsonl`ファイルに追記しなければならない。

### 要件カテゴリG: シンボル定義位置の特定 (Symbol Location)

- 要件 G-1: シンボル定義の行範囲およびファイルパスの特定
   - ユーザーストーリー
      - 私はAI開発エージェントとして、特定のシンボルの実装コード自体を取得せずに、その定義位置（ファイルパス、開始行、終了行）のみを特定したい。なぜなら、無駄なコード読み込みを省いてトークン効率の良い部分読み込みを行うためだ。
   - 受け入れ基準
      - エージェントが対象ファイルのパスとシンボル名を指定して`locate`コマンドで位置特定を要求したとき、システムは該当シンボルの定義元ファイル、開始行、終了行を解決し、`file_path:start_line-end_line`の形式で出力しなければならない。
      - `--json`が指定された場合、システムは`file`、`symbol`、`start_line`、`end_line`を含むJSONオブジェクトを出力しなければならない。

### 要件カテゴリH: エージェント運用品質の強化 (Agent Operability Hardening)

- 要件 H-1: `agent-context` スキーマの完全性
   - 実装済みの全オプション（`--json`/`-j` を含む）を漏れなく反映する。CLIのコマンド定義とスキーマ定義の間に乖離が生じない設計とすること。
- 要件 H-2: 大規模出力コマンドの上限制御と切り詰めヒント
   - `references` の `--limit`、`outline`/`symbol` の閾値（300行）超過時の自動切り詰めと `--no-truncate` を提供する。
- 要件 H-3: アクション可能なエラーメッセージの強化
   - シンボル未検出時に実在するシンボル名候補を提示する。
- 要件 H-4: 終了コードのタクソノミー
   - エラー種別ごとに一貫した終了コードを定義・適用する。
- 要件 H-5: タスクベースのスキルマニフェスト（`SKILL.md`）の提供
   - 推奨ワークフロー（`directory` → `outline` → `locate` → `symbol` → `references`）は、独立した `SKILL.md` としてルートに配置する。セットアップ情報は `README.md` に記載し、ワークフローの説明とは分離する。
- 要件 H-6: `--json` フラグ規約との整合
   - JSON出力の要求は `--json`（ブールフラグ、ショートハンド `-j`）に統一・一本化する。

### 要件カテゴリI: ビルド・配布 (Build & Distribution)

- 要件 I-1: シングルバイナリでの実行
   - ユーザーストーリー
      - 私はAI開発エージェント運用者として、Pythonランタイムやライブラリのインストールなしに ast-digger を実行したい。なぜなら、CI環境やコンテナ内での依存関係セットアップの手間とレイテンシを削減するためだ。
   - 受け入れ基準
      - `go build ./cmd/ast-digger` によって、外部ランタイムのインストールを必要としない単一の実行可能バイナリが生成されなければならない。
      - 生成されたバイナリは、tree-sitter バインディングのビルド時にCGOを要する場合であっても、実行時には追加の共有ライブラリファイルの同梱・配置なしに単独で動作しなければならない（静的リンクを前提とする）。
      - **プラットフォーム別の例外**: Windows / Linux では上記を必須（MUST）とする。macOSはAppleのOS制約により完全な静的リンクができないため（[`tech.md`](./tech.md) 参照）、システムライブラリへの動的リンクを許容し、可能な範囲での静的リンク（ベストエフォート）を目標とする。

### 要件カテゴリJ: 将来機能拡張 (Backlog)

- 要件 J-1 (タスク25対応): 対応言語・拡張子一覧のプログラム的提示 (セルフインスペクション強化)
   - ユーザーストーリー
      - 私はAI開発エージェントとして、`ast-digger` がどのプログラミング言語・ファイル拡張子に対応しているかをプログラム的・機械可読に自律把握したい。なぜなら、解析対象ファイルの対応可否を事前判定し無駄な呼び出しエラーを防ぐためだ。
   - 受け入れ基準
      - `agent-context` サブコマンドの出力JSONメタデータに `"supported_languages"` および `"supported_extensions"` フィールドが含まれなければならない。
      - ルートコマンドおよび各サブコマンドの `--help` 説明文に対応言語一覧が明記されていなければならない。

- 要件 J-2 (タスク26対応): インポート依存コードの自動追跡抽出 (`--follow-imports`)
   - ユーザーストーリー
      - 私はAI開発エージェントとして、指定したシンボルが依存しているローカルモジュールのコード実体も同時に取得したい。なぜなら、ツール呼び出しのターン数を削減しコンテキスト探索を爆速化するためだ。
   - 受け入れ基準
      - `symbol` サブコマンドに `--follow-imports` オプションを提供しなければならない。
      - `--follow-imports` 指定時、指定シンボルのコード抽出に加え、インポート定義解決（`ResolveImports`）と連鎖して依存先コード本文を構造化データとして同時に返却しなければならない。
      - 循環インポートプロジェクトにおいて無限ループにならず訪問済み判定により安全に停止しなければならない。

### 要件カテゴリK: Markdownドキュメント構造解析 (Markdown Document Structure Parsing)

- 要件 K-1: Markdownファイルのスケルトン（目次・見出し・コードブロック位置）抽出
   - ユーザーストーリー
      - 私はAI開発エージェントとして、長大なMarkdownドキュメントの文章本文（ノイズ）を読まずに、見出し階層（H1〜H6）および埋め込まれたコードブロック（Mermaidダイアグラム等）の構造と位置を把握したい。なぜなら、トークン消費を抑えてドキュメント全体像を即座に理解するためだ。
   - 受け入れ基準
      - エージェントがMarkdownファイル（`.md`, `.markdown`）のパスを指定して`outline`コマンドを実行したとき、システムは `tree-sitter-markdown` を用いて構文パースし、見出し階層（H1〜H6）を保持した骨格コードを出力しなければならない。
      - 本文テキスト部分は消去または省略しつつ、セクション内にコードブロックが存在する場合、その言語名と行範囲（例: `<!-- [code_block:mermaid] L50-L75 (26 lines) -->`）をアウトライン上に明示しなければならない。
      - 見出しレベルが飛躍している場合（例: H2 の直後に H4）であっても、直近の上位レベル見出しの配下としてネスト構造を判定し、パースを継続しなければならない。
      - 閉じられていないコードブロック等の不完全なMarkdownであっても、パース可能な見出し・コードブロック構造を抽出して出力しなければならない。

- 要件 K-2: 見出しパス指定によるセクションおよびコードブロックのピンポイント抽出
   - ユーザーストーリー
      - 私はAI開発エージェントとして、Markdown内の特定の見出しセクション全文、または特定のコードブロック（例: Mermaidの構成図）だけをピンポイントで取得したい。なぜなら、必要なドキュメントの章や図だけを抽出してLLMに提示するためだ。
   - 受け入れ基準
      - エージェントがMarkdownファイルパスと見出しパス（例: `アーキテクチャ/新しい言語の追加` や `アーキテクチャ/code_block:mermaid`）を指定して `symbol` または `locate` コマンドを実行したとき、システムは該当する見出しセクション（該当見出し開始行〜同等以上のレベルの見出しの直前行）または該当コードブロックのコード本文／行範囲を正確に抽出して返却しなければならない。
      - 同一セクション内に同種のコードブロックが複数存在する場合、`code_block:go#1` や `code_block:go#2` などのインデックス指定によって個別に特定・抽出できなければならない。
      - 見出し名にスラッシュ（`/`）や特殊文字が含まれる場合、エスケープ（`\/`）または引用符で囲むことでパス区切り文字と区別して解決できなければならない。
      - 同名のアウトライン（見出し）が複数存在する場合、親見出しからのフルパス指定によって一意に特定できなければならない。一意に特定できない場合は類似見出しの候補を提示し終了コード4を返さなければならない。

- 要件 K-3: Markdown内相対リンク・アンカーの依存関係解決
   - ユーザーストーリー
      - 私はAI開発エージェントとして、Markdown内に記述された他のMarkdownファイルへのリンクやアンカーの参照先を特定したい。なぜなら、関連ドキュメント間を自律的に横断して調査するためだ。
   - 受け入れ基準
      - エージェントがMarkdownファイルとシンボル（見出し名またはリンクテキスト）を指定して `resolve-import` または `references` コマンドを実行したとき、システムはドキュメント内の相対ファイルリンク（例: `[設計](SPECS/design.md#architecture)`）やセクション参照（例: `[章2](#section-2)`）を解析し、定義元のファイルパスと開始行を返却しなければならない。

- 要件 K-4: YAML/TOML Frontmatter（フロントマター）メタデータの解析・抽出
   - ユーザーストーリー
      - 私はAI開発エージェントとして、Markdownファイルの先頭に存在する Frontmatter メタデータ（`---` で囲まれたYAML等）の位置と内容を把握・抽出したい。なぜなら、見出し構造と区別しつつドキュメントのメタ情報（タイトル、タグ、著者等）を取得するためだ。
   - 受け入れ基準
      - エージェントが Markdown ファイルをパースした際、システムは先頭の Frontmatter ブロックを `frontmatter` という疑似シンボルとして識別し、見出し階層と混同せずに解析しなければならない。
      - `outline` コマンドにおいて、Frontmatter が存在する場合は `<!-- [frontmatter] L1-L6 (title, tags, author) -->` の形式でスケルトンにメタデータ領域を明示しなければならない。
      - `symbol` または `locate` コマンドで `frontmatter` を指定した場合、システムは Frontmatter の内容全体または行範囲を抽出・特定して返却しなければならない。

### 要件カテゴリL: SQLドキュメント・CTE構造解析 (SQL Document & CTE Outline Extraction - Snowflake Dialect)

- 要件 L-1: SQLファイルのスケルトン（CTE一覧・DAG依存関係・ステートメント骨格）抽出
   - ユーザーストーリー
      - 私はAI開発エージェントとして、数千行に及ぶ長大なバッチ処理SQL（Snowflake/DWH）のクエリ本文（ノイズ）を読まずに、どのようなCTE（Common Table Expression）やステートメントで構成され、CTE同士や実テーブルがどのように依存し合っているかのデータフロー（DAG）を把握したい。なぜなら、トークン消費を抑えてリファクタリングの全体像を即座に理解するためだ。
   - 受け入れ基準
      - エージェントがSQLファイル（`.sql`）のパスを指定して`outline`コマンドを実行したとき、システムは `tree-sitter-sql` を用いて構文解析し、`WITH` 句内の各CTE名、開始行・終了行、依存する参照テーブル/上流CTE一覧（`depends_on`）、および出力カラム一覧を含むスケルトンを出力しなければならない。
      - 各CTE内部のクエリ本文は省略（`/* ... */`）され、全体のデータフロー構造を最小トークンで提示しなければならない。
      - Snowflake固有の構文（`QUALIFY`、`MERGE INTO`、`LATERAL FLATTEN`、`COPY INTO`、`CREATE OR REPLACE TABLE AS` 等）を含むSQLであっても、パースエラーを起こさずCTE階層とメインステートメントを正しく識別して出力しなければならない。
      - `--json` オプション指定時、各CTEの名称、行範囲、依存先一覧（`depends_on`）、および内包するサブクエリ添字情報を構造化JSONとして返却しなければならない。

- 要件 L-2: CTEのピンポイントコード抽出と上流依存の自動追跡 (`symbol`, `--follow-imports`)
   - ユーザーストーリー
      - 私はAI開発エージェントとして、リファクタリング対象の特定CTEの実装コードだけを取得したい。また、そのCTEの計算に必要な上流CTE群だけを一括して芋づる式に読み込みたい。なぜなら、無関係な他の大量のCTEを排除し、最小限のコンテキストで安全にコード修正するためだ。
   - 受け入れ基準
      - エージェントがSQLファイルとCTE名（例: `ast-digger symbol query.sql cte_sales`）を指定したとき、システムは該当CTEの定義ブロック（`cte_sales AS (SELECT ...)`）のみをピンポイントで抽出して返却しなければならない。
      - エージェントが `--follow-imports` オプションを付与した場合、システムは対象CTEが `FROM` や `JOIN` 等で参照している上流のCTE群を再帰的に追跡し、依存チェーンに含まれるCTE定義コードのみを依存順序に沿って一括連結（またはJSON配列）して返却しなければならない。
      - 循環参照や自己参照（`WITH RECURSIVE`）が存在する場合であっても、訪問済み管理により無限ループを起こさず安全に探索を停止しなければならない。

- 要件 L-3: インデックス添字による名前なしサブクエリの特定・抽出 (`locate`, `symbol`)
   - ユーザーストーリー
      - 私はAI開発エージェントとして、SQLの `WHERE IN (...)` や `FROM (...)` などの深いネストに潜む名前のないサブクエリを新しいCTEに外出しリファクタリングしたい。そのため、サブクエリの正確な行範囲を特定し、そのクエリ本文だけを取り出したい。
   - 受け入れ基準
      - エージェントが親CTE名とインデックス添字（例: `cte_orders/subquery[0]` または `cte_orders/subquery#0`）、あるいはフラットな添字（`subquery[0]`）を指定して `locate` コマンドを実行したとき、システムは該当サブクエリの開始行・終了行（例: `query.sql:120-145`）を正確に返却しなければならない。
      - エージェントが同様のパスを指定して `symbol` コマンドを実行したとき、システムは該当サブクエリのコード本文のみを抽出して返却しなければならない。
      - サブクエリにエイリアスが付与されている場合（例: `FROM (SELECT ...) AS sub_items`）、エイリアス名（`cte_orders/sub_items`）および添字（`cte_orders/subquery[0]`）の双方向で特定可能でなければならない。

- 要件 L-4: CTEおよび実テーブルの参照箇所探索・依存解決 (`references`, `resolve-import`)
   - ユーザーストーリー
      - 私はAI開発エージェントとして、特定のCTEや大元テーブルを変更・削除した際の影響範囲（下流で参照しているCTE一覧）を特定したい。
   - 受け入れ基準
      - エージェントがシンボル名（CTE名またはテーブル名）を指定して `references` コマンドを実行したとき、システムはSQLファイル内（およびプロジェクト全体）から該当シンボルを参照（`FROM`, `JOIN`, `MERGE USING` 等）している行番号と行内容を抽出して返却しなければならない。
      - エージェントがCTE名を指定して `resolve-import` コマンドを実行したとき、システムは該当CTEが定義されている行番号を即座に解決して返却しなければならない。

- 要件 L-5: 重複テーブル・CTE参照探索と集約分析 (Duplicate Scan & Reference Tracing for SNOW-005)
   - ユーザーストーリー
      - 私はAI開発エージェントとして、`icepick` の `DuplicateTableScanRule` (SNOW-005) 等で検出された「複数CTEにまたがる同一テーブルの重複スキャン」を解消するため、対象テーブルを参照しているすべてのCTEと行番号を一覧特定し、共通CTEに集約するための比較材料を取得したい。
   - 受け入れ基準
      - エージェントがテーブル名（例: `ast-digger references raw_orders`）を指定したとき、システムは単一SQLファイル内のどのCTE（およびメインステートメント）がそのテーブルを参照しているかを網羅的に抽出して返却しなければならない。
      - エージェントが重複参照している各CTEを指定して `symbol` コマンドを実行したとき、それぞれのフィルタ条件（WHERE句）や射影カラムを比較できるように、該当CTEコードを独立して迅速に取得できなければならない。

- 要件 L-6: 相関サブクエリおよびネスト派生テーブルの外科的抽出 (Correlated & Nested Subquery Extraction for SNOW-002, SNOW-007)
   - ユーザーストーリー
      - 私はAI開発エージェントとして、`icepick` の `CorrelatedSubqueryRule` (SNOW-002: 相関サブクエリ) や `NestedSubqueryRule` (SNOW-007: ネストされた派生テーブル) を修正するため、親クエリのWHERE/SELECT/JOIN句に潜むサブクエリの正確な行位置とコード本文を取得し、独立したCTEへの外出しおよび `LEFT JOIN` 化を行いたい。
   - 受け入れ基準
      - システムは `tree-sitter-sql` の構文解析を通じて、親CTE内部に存在するサブクエリノードを自動検出し、`subquery[0]`, `subquery[1]` などの出現順添字パスでアクセス可能にしなければならない。
      - エージェントが `locate` コマンドを実行したとき、サブクエリ置換対象の正確な行範囲（例: `L120-L145`）および外出し先となる親CTEの定義開始行（例: `L80`）をピンポイントで返却し、最小限の差分置換（外科手術的リファクタリング）を可能にしなければならない。

- 要件 L-7: ビュー定義（CREATE VIEW）のシンボル名認識と警告出力の最適化
   - ユーザーストーリー
      - 私はAI開発エージェントとして、`CREATE VIEW`、`CREATE SECURE VIEW`、`CREATE MATERIALIZED VIEW`、`CREATE DYNAMIC TABLE` 等で定義されたSQLファイルから、ビュー名/テーブル名を直接シンボル名として指定してビュー定義全体（`CREATE ... AS SELECT ...`）をピンポイント抽出したい。また、複数回のパース時に同じ構文警告がコンソールに連打されるノイズを排除したい。
   - 受け入れ基準
      - エージェントが `CREATE [OR REPLACE] [SECURE | MATERIALIZED | TRANSIENT | RECURSIVE] VIEW <view_name>` や `CREATE [TRANSIENT | DYNAMIC] TABLE <table_name>` を含むSQLファイルを解析したとき、システムは `main_query` ではなく実際のビュー名/テーブル名を `Kind: "statement"` のシンボル名として抽出しなければならない。
      - エージェントがビュー名を指定して `locate` または `symbol` コマンドを実行したとき、システムは該当ビュー定義全体の開始行・終了行およびコード本文を返却しなければならない。
      - 同一SQLファイルに対する構文警告（`Warning: Syntax errors or dialect extensions detected in ...`）は、同一プロセス実行内で1ファイルにつき最大1回のみ出力し、重複連打を抑止しなければならない。
